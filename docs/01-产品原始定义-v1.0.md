# 1. 产品概述

## 1.1 产品定义

构建一个独立的网页交互体验，帮助普通用户理解语言模型如何处理输入并生成答案。

用户输入一个真实问题。系统在展示最终答案之前，先通过以下方式将模型生成过程可视化：

1. 使用能够从模型中读取的真实数据；
2. 使用基于真实机制的解释性可视化；
3. 使用被明确区分的、非字面意义上的视觉隐喻。

只有在生成过程展示完成之后，最终答案才会出现。

## 1.2 核心目的

这不是一个以提升聊天效率为主要目标的工具。

这个产品存在的目的是帮助用户理解：

- 模型如何处理文本；
- 回答如何逐 Token 生成；
- 为什么每一步生成都存在多个可能的延续方向；
- 为什么模型输出可能与人的预期不同；
- 模型能够做什么、不能做什么；
- 为什么一个不令人满意的输出，并不只是因为模型“很蠢”。

## 1.3 目标用户

目标用户是：

- 使用过聊天类 AI 或图像生成工具；
- 不了解 AI 模型工作流机制；
- 容易把模型输出理解成模型像人类一样进行了完全相同的理解和推理。

## 1.4 产品形态

- 独立网站
- 聊天式输入与对话界面
- 实时模型处理过程可视化
- 多轮对话
- 用户只能观看过程，不能干预生成

暂定描述：

> 交互式 AI 模型机制体验网站

不要将其定位为普通聊天机器人，也不要将其定位为通用科普文章网站。

# 2. 产品原则

## 2.1 真实性原则

每一个视觉元素都必须属于以下三类之一：

### A. 真实数据

直接来自：

- 用户输入；
- Tokenizer 输出；
- 模型生成输出；
- 模型 Logits 或概率数据；
- 对话历史。

### B. 机制解释

基于自回归语言生成机制设计的可视化，但不是对模型内部主观思维的直接记录。

例如：

- Token 之间以视觉方式相互影响；
- 上下文被重新计算；
- 候选 Token 出现；
- 被选中的 Token 加入已有序列。

### C. 无法获得的内部内容

以下内容不能被当作真实内容展示：

- 模型完整的内部想法；
- 模型的主观意图；
- 模型真实的情绪理解；
- 模型为什么选择某个回答方向的完整原因；
- 完整思维链；
- 声称模型“决定先安慰用户”或“真正理解了悲伤”。

## 2.2 必须向用户明确区分

界面必须区分：

- 真实模型数据；
- 解释性机制可视化；
- 无法获取或不展示的内部信息。

最终视觉风格尚未确定，但产品架构必须支持这种区分。

## 2.3 产品体验原则

生成过程是产品的主要体验，而不是一个加载动画。

不能为了让答案更快出现，就把可视化过程压缩掉。

# 4. 核心用户流程

```text
用户打开网站
        ↓
用户看到聊天式界面
        ↓
用户输入一个普通文字问题
        ↓
系统校验输入长度
        ↓
系统将当前输入与对话历史合并
        ↓
系统对上下文进行 Tokenization
        ↓
系统开始模型生成
        ↓
每一步生成过程：
    1. 计算下一个 Token 的 Logits；
    2. 将 Logits 转换为概率；
    3. 提取 Top-5 候选 Token；
    4. 记录实际被选中的 Token；
    5. 将本步数据发送给前端；
    6. 可视化候选、概率和选择结果；
    7. 将被选中的 Token 加入序列；
    8. 继续下一步。
        ↓
生成结束
        ↓
最终答案出现在聊天记录中
        ↓
用户可以输入下一个问题
        ↓
上一轮对话成为下一轮上下文的一部分
```

# 5. 三层产品模型

## 5.1 第一层：核心模型流程

| 步骤 | 模型流程 | 说明 |
|---|---|---|
| 1 | 接收上下文 | 当前问题加相关对话历史 |
| 2 | Tokenization | 将文本转换为模型 Token 和 Token ID |
| 3 | 上下文计算 | 模型根据当前序列计算下一个 Token 的分布 |
| 4 | 生成候选 | 生成所有可能下一个 Token 的概率分布 |
| 5 | 提取 Top-5 | 选取概率最高的 5 个候选用于展示 |
| 6 | Token 选择 | 根据生成参数选择实际的下一个 Token |
| 7 | 更新上下文 | 将选中的 Token 加入已生成序列 |
| 8 | 重复 | 使用更新后的序列重新计算下一 Token 分布 |
| 9 | 完成 | 到达停止条件并返回最终答案 |

## 5.2 第二层：真实数据层

| 数据字段 | 真实或模拟 | 来源 | MVP 是否需要 |
|---|---|---|---|
| 用户输入 | 真实 | 用户 | 是 |
| 对话历史 | 真实 | 应用状态 | 是 |
| 合并后的模型上下文 | 真实 | 后端 | 是 |
| Token 文本 | 真实 | Tokenizer | 是 |
| Token ID | 真实 | Tokenizer | 是 |
| 生成步骤编号 | 真实 | 后端生成循环 | 是 |
| Top-5 候选 Token | 真实 | 模型 Logits | 是 |
| 候选概率 | 真实 | Logits 经 Softmax 转换 | 是 |
| 被选中的 Token | 真实 | 模型生成结果 | 是 |
| 被选中 Token 的概率 | 真实 | 候选分布 | 是 |
| 当前已生成序列 | 真实 | 后端生成状态 | 是 |
| 最终答案 | 真实 | 模型 | 是 |
| Token 之间的视觉连线 | 解释性 | 产品可视化 | 否，不是真实数据 |
| 模型完整想法 | 无法获取 | 不可访问 | 必须不展示 |
| 回答方向的完整原因 | 无法获取 | 不可访问 | 必须不展示 |

## 5.3 第三层：可视化层

| 真实机制或数据 | 视觉行为 | 分类 |
|---|---|---|
| 用户输入 | 原始句子进入视觉流程 | 真实内容的可视化 |
| Tokenization | 句子拆分为 Token 块 | 真实数据的可视化 |
| Token ID | 可选的次级技术标签 | 真实数据的可视化 |
| 上下文计算 | Token 块形成变化中的关系或影响结构 | 机制解释 |
| Top-5 候选 | 出现 5 个候选 Token 对象 | 真实数据的可视化 |
| 候选概率 | 使用条形、大小、位置或其他定量编码 | 真实数据的可视化 |
| 实际选择 | 某个候选被突出并被选中 | 真实结果的可视化 |
| 更新上下文 | 选中的 Token 加入逐步增长的回答 | 真实过程的可视化 |
| 下一步生成 | 上下文更新后，候选集合发生变化 | 真实数据的可视化 |
| 生成完成 | 完整答案进入聊天记录 | 真实输出的可视化 |

> 机制可视化用于解释模型架构，但不能被描述为模型完整的内部思维。

# 7. 多轮对话逻辑

## 7.1 已确认行为

MVP 支持多轮对话。

```text
第一轮：
用户问题
→ 过程可视化
→ 模型回答

第二轮：
之前的对话 + 新的用户问题
→ 过程可视化
→ 模型回答
```

## 7.2 上下文行为

每一轮新对话中：

- 之前的用户消息和模型回答都会进入模型上下文；
- 当前用户输入被追加；
- 完整上下文被 Tokenization；
- 模型基于更新后的上下文继续生成。

## 7.3 历史对话的视觉呈现

尚未确定。

后续可能方案：

- 将所有历史消息作为 Token 组展开；
- 将之前的消息压缩为一个“对话历史”模块；
- 只展示最新一轮，并提示早期上下文仍然生效。

不要自动做出这一设计决定。可视化架构必须保留扩展性。

# 8. 输入与输出限制

## 8.1 输入

- 仅文字
- 普通问答请求
- 最大约 100 个中文字符
- 用户不需要选择任务类型
- MVP 中不支持图片或文档上传

## 8.2 输出

- 答案必须足够短，便于进行逐 Token 可视化
- 模型必须在明确的最大 Token 数达到时停止
- 最终停止条件必须可配置

# 10. 技术要求

## 10.1 模型要求

使用一个能够访问以下内容的开源因果语言模型：

- Tokenizer；
- Token ID；
- 每一步生成的 Logits；
- 已生成 Token ID；
- 生成参数；
- 对话上下文。

不要使用只能返回最终答案、并隐藏 Token 级概率的模型或 API。

## 10.2 后端生成行为要求

不能只依赖标准流式文本 API。

后端必须运行或封装生成循环，使每一步都能返回结构化数据。

步骤数据示例：

```json
{
  "step": 12,
  "context_token_count": 48,
  "generated_text_so_far": "模型并不是先想好完整答案",
  "top_candidates": [
    {
      "token_id": 123,
      "token_text": "，",
      "probability": 0.31
    },
    {
      "token_id": 456,
      "token_text": "再",
      "probability": 0.22
    },
    {
      "token_id": 789,
      "token_text": "而",
      "probability": 0.16
    },
    {
      "token_id": 234,
      "token_text": "它",
      "probability": 0.10
    },
    {
      "token_id": 567,
      "token_text": "然后",
      "probability": 0.07
    }
  ],
  "selected_token": {
    "token_id": 123,
    "token_text": "，",
    "probability": 0.31
  }
}
```

## 10.3 后端职责

- 维护多轮对话状态；
- 校验输入长度；
- 格式化对话上下文；
- 对上下文进行 Tokenization；
- 逐步运行生成；
- 读取 Logits；
- 将 Logits 转换为概率；
- 提取 Top-5 候选 Token；
- 确认实际被选中的 Token；
- 将每一步生成数据流式发送给前端；
- 返回最终答案；
- 处理停止 Token 和最大输出长度；
- 处理错误和模型不可用情况。

## 10.4 前端职责

- 聊天界面；
- 输入校验；
- 对话历史展示；
- 模型处理过程可视化容器；
- Tokenization 可视化；
- 候选 Token 可视化；
- 概率可视化；
- 被选中 Token 的动画；
- 已生成序列展示；
- 最终答案展示；
- 区分真实数据和解释性可视化；
- 加载、错误和完成状态。

## 10.5 建议通信方式

使用以下任一种：

- WebSocket；
- Server-Sent Events；
- 流式 HTTP 响应。

传输方式必须支持逐步发送结构化生成事件。

# 13. MVP 验收标准

只有满足以下全部条件，MVP 才算完成。

## 13.1 功能验收

- 用户可以提交一个文字问题；
- 输入长度能够被校验；
- 多轮对话可以工作；
- 之前的对话会进入后续上下文；
- 可以获得真实 Tokenizer 输出；
- 可以获得 Token ID；
- 模型按 Token 逐步生成；
- 每一步都会返回 Top-5 候选；
- 每个候选都有真实概率；
- 实际被选中的 Token 被记录；
- 生成过程结束后展示最终答案；
- 输出长度受到控制。

## 13.2 真实性验收

- 不展示伪造概率；
- 不展示编造的候选 Token；
- 不展示伪造思维链；
- 不声称解释性视觉就是模型精确的内部思维；
- 真实数据和机制解释能够被区分。

## 13.3 UX 验收

- 用户能够清楚看到输入如何转换为 Token；
- 用户能够清楚看到多个候选 Token；
- 用户能够清楚看到哪个 Token 被选中；
- 用户能够看到回答逐 Token 增长；
- 用户能够区分过程视图和最终聊天答案；
- 用户能够继续进入下一轮对话。

# 14. 非 MVP 扩展路线

以下功能必须被记录，但第一版不实现。

## 14.1 Embedding 与语义相似度

目的：

- 解释语义搜索；
- 解释推荐；
- 解释文本如何变成向量；
- 解释为什么两段内容可能被认为相似。

可能流程：

```text
用户输入
→ 文本编码
→ Embedding 向量
→ 与其他向量比较
→ 相似度分数
→ 最近结果
```

可能获得的真实数据：

- 输入文本；
- Embedding 向量；
- 相似度分数；
- 最近邻结果；
- 检索排序。

不能声称每个 Embedding 维度都具有明确的人类可读含义。

## 14.2 RAG

可能流程：

```text
用户问题
→ 查询向量
→ 检索文档
→ 选择相关片段
→ 将片段加入模型上下文
→ 生成答案
```

核心学习点：

- 答案可能依赖检索到的外部内容；
- 错误检索可能产生错误回答；
- 模型输出并不总是只来自模型参数。

## 14.3 图像生成

可能流程：

```text
Prompt
→ Prompt Tokenization
→ 文本编码
→ 初始噪声 / Latent
→ 迭代去噪
→ Latent 解码
→ 最终图片
```

使用开放 Diffusion 模型时可能获得的真实数据：

- Prompt；
- Prompt Token；
- Seed；
- 生成步数；
- Guidance 值；
- 初始噪声；
- 中间 Latent 状态；
- 中间解码图片；
- 最终图片。

不能声称：

- 模型先想象出一张完整图片；
- 每一个 Prompt 词都唯一映射到某个图像区域；
- Latent 空间就是可以直接解释的内部草图。

## 14.4 图像理解

可能流程：

```text
上传图片
→ 图像 Patch 或视觉编码
→ 视觉表示
→ 与文本上下文结合
→ 生成文字回答
```

## 14.5 用户控制生成实验

未来可能支持：

- Temperature；
- Top-p；
- Seed；
- 候选 Token 选择；
- 使用相同输入重新运行；
- 比较两条生成路径；
- 比较两个模型。

这些都不属于 MVP。

# 15. AI / Codex 与产品负责人的职责

## 15.1 Codex 可以协助完成

- 仓库初始化；
- 前端脚手架；
- 后端脚手架；
- 模型接入；
- Tokenizer 接入；
- 自定义生成循环；
- Logits 处理；
- 概率计算；
- Top-5 提取；
- 流式数据协议；
- 状态管理；
- 数据结构；
- 聊天 UI 实现；
- 可视化组件实现；
- 在视觉规则确定后的动画实现；
- 测试；
- 错误处理；
- 部署；
- 技术文档。

## 15.2 产品负责人必须决定

- 最终产品定位；
- 每一步用户必须理解什么；
- 视觉隐喻；
- 拟人化程度；
- 视觉世界；
- 信息层级；
- 真实数据和解释如何被标记；
- 视觉节奏；
- 对话历史如何呈现；
- 最终交互和视觉验收；
- 用户测试任务；
- 产品是否容易理解且不会误导。

Codex 不能自行编造模型的“思考过程”，也不能把解释性动画当作事实性的内部轨迹呈现。

# 16. Codex 的下一步要求

不要立即开始完整实现。

首先产出一份技术可行性与实施方案，包含：

1. 推荐满足 Token 级 Logits 访问要求的开源语言模型；
2. 每个模型的预计算力要求；
3. MVP 推荐的最终模型；
4. 前端技术选型；
5. 后端技术选型；
6. 模型服务架构；
7. 生成步骤流式传输架构；
8. 前后端之间的精确数据协议；
9. 仓库目录结构；
10. 开发里程碑；
11. 技术风险；
12. 如果本地托管模型成本过高时的备用方案；
13. 最小垂直切片原型方案。

第一个垂直切片只需要证明：

```text
一个用户问题
→ 真实 Tokenization
→ 模型生成
→ 每一步 Top-5 候选和概率
→ 实际被选中的 Token
→ 在基础界面中展示结构化步骤数据
→ 最终答案
```

在技术数据链路被验证之前，不要把时间花在最终视觉风格上。

---

# 17. 实现顺序

```text
阶段 1：技术可行性
选择模型并验证 Logits 可访问

阶段 2：数据链路原型
输入 → Tokenizer → 生成循环 → Top-5 → 被选中 Token → 最终答案

阶段 3：基础网页界面
聊天输入 + 过程面板 + 最终答案

阶段 4：多轮上下文
后续生成中包含对话历史

阶段 5：可视化系统
将真实数据映射为视觉状态

阶段 6：最终视觉设计
加入隐喻、风格、动态和解释标签

阶段 7：用户测试
验证用户是否能够正确理解模型行为和局限
```

---

# 18. 最终确认的产品说明

> MVP 是一个支持多轮对话、仅文字输入的网页体验。普通用户可以输入自己的问题，并观看语言模型如何逐 Token 生成回答。系统展示真实 Tokenization 数据、真实 Top-5 下一 Token 候选、真实概率、实际被选中的 Token 和最终答案。解释性可视化用于帮助用户理解模型机制，但绝不能被呈现为模型完整的内部思维或思维链。图像生成、Embedding、RAG、工具、Agent 和用户控制生成都被记录为后续扩展方向，并明确排除在 MVP 之外。
